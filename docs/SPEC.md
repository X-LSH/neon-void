## 1. 坐标系与逻辑画布

- **逻辑画布固定 480 × 720**（2:3 竖版），与屏幕尺寸完全解耦。
- 缩放 `scale = min(cssW / 480, cssH / 720)`，**浮点**不加取整（矢量图形不需要光栅对齐）。
- 画布铺满视口，**游戏区域居中**，两侧/上下留边由 DOM 侧栏与 HUD 填充，背景星空**不受游戏区裁剪**（铺满全屏，边框外的星空更暗）。
- 这不会浪费桌面空间：宽屏侧栏放 HUD（分数/连击/生命/波次/道具计时），窄屏改为顶部 HUD 条。

> **为什么画布尺寸必须固定**：难度以「弹幕密度」度量，而密度依赖可用面积。
> 可变的游戏区 = 不同屏幕上的难度不同 = 排行榜失去可比性。这是射击游戏与平台跳跃的关键差异。

### 1.1 固定步长 1/60s + 扫掠碰撞

60Hz 下玩家子弹 760 u/s 每步走 12.7 单位，而「子弹半径 3.2 + 敌机半径 11」= 14.2 ——
**离散点检测会在边界处漏判（穿透）**。

**对策：子弹碰撞一律用上一帧位置到当前位置的线段做扫掠检测**（线段–圆最近距离 ≤ 半径和）。
不用 1/120 步长的理由：扫掠检测的代价 O(1)，加倍步长却是全域 2 倍成本。

**回归看守**：`verify.mjs` 对 760 u/s 子弹扫过 11 半径目标做**逐子偏移压力测试**，任何子偏移漏判即失败。

## 2. 分层单向依赖

```
scenes → ui → render → game → core
                     ↘ core
```

| 层 | 职责 | 硬约束 |
| --- | --- | --- |
| `core/` | 循环、输入、视口、音频、存档、PRNG | **不含任何游戏语义** |
| `game/` | 物理、状态机、波次、碰撞、计分 | **不碰 DOM、不碰 Canvas、不碰 Audio** —— 这是自检能在 Node 裸跑的前提 |
| `render/` | 只读绘制 | **不得修改任何游戏状态** |
| `ui/` | DOM 面板与 HUD | 不直接改游戏状态，只能发意图 |
| `scenes/` | 场景切换与装配 | 唯一同时接触输入/更新/渲染的层 |

`game/` 通过 `world.events` 队列向外广播「发生了什么」（`enemyDie` / `pickup` / `playerHit` …），
由 `scenes/battle.js` 统一转成粒子、音效、震动。**这就是 game 层不需要认识渲染与音频的实现方式。**

## 3. 输入抽象

游戏逻辑永远不知道输入来自键盘还是手指。

```js
intent() → {
  move: {x, y},              // 归一化方向（键盘/摇杆）
  pointer: {active, x, y},   // 游戏区坐标（触屏拖拽），active 时优先于 move
  confirm: {pressed},        // 边沿
  pause:   {pressed},
  mute:    {pressed},
}
```

- `pressed` 用**计数锁存**而非布尔：一帧可能推进多个物理步（边沿只该被第一步消费），也可能零个（信号必须留到下一帧，**输入绝不丢失**）。
- 触屏与键盘写**同一份** held/pending —— `core/touch.js` 里的几何是纯函数（偏移、裁剪、指数逼近），可在 Node 逐条断言。

### 3.1 触屏用「绝对定位 + 垂直偏移」

PRD 写「手指拖拽飞船移动」。直接让飞船落在手指正下方会被拇指完全盖住，
所以在游戏区内减去一个固定纵向偏移（约 38 逻辑单位），使飞船浮在手指上方。
`clampToField` 保证边缘处仍可到达四角。

## 4. 难度曲线（时间驱动，无波间停顿）

**波次由时间驱动**（不是「清空才进下一波」）：连续下卷无死气，且不会因为残留一只敌机卡住节奏。

```
waveDuration(w) = max(9, 15 − (w−1) × 0.25)
events(w)       = min(34, 5 + w × 0.85)             // 每波的「生成事件」数
分组人数         scout 2–4 · striker 2–3 · seeker 1–2 · tank 1 · elite 1
                 （每 8 波上限 +1，封顶 5）
事件间距         (剩余时间 ÷ 剩余事件数) × 抖动[0.7, 1.3]，下限 0.3s
speedMul(w)     = 1 + min(0.55, (w−1) × 0.018)
hpMul(w)        = 1 + min(1.00, (w−1) × 0.030)     // 计算后向上取整，至少 1
fireMul(w)      = max(0.55, 1 − (w−1) × 0.015)     // 越小越快
```

**间距必须由「剩余时间 ÷ 剩余事件数」推导，不能用固定区间**：
固定区间配上固定事件数，早期波次（预算小、时长长）会出现十几秒空场 ——
新手在热身阶段面对空屏，是「这游戏是不是卡住了」而不是「轻松」。

解锁门槛：`striker 6` / `seeker 9` / `tank 16` / `elite 18`；**Boss 每 10 波**（10, 20, 30…），Boss 波期间只零星补侦察机。

### 4.1 单局时长标尺（3–8 分钟目标）

按上述公式解析推算：

| 到达波次 | 累计时长 |
| --- | --- |
| 第 10 波 Boss 结束 | ≈ 2:46 |
| 第 20 波开始 | ≈ 4:47 |
| 第 30 波开始 | ≈ 6:32 |
| 第 31 波 Boss 结束 | ≈ 8:35 |

中等玩家死在 18–24 波 → **4–6 分钟** ✓；高手到 30 波 → **8 分钟** ✓。
`scripts/balance.mjs` 把这个表实测回来，**不从公式反推**。

### 4.2 实测标尺（2026-09-20，7 种子）

| 档位 | 单局时长 | 到达波次 | 受击/分 |
| --- | --- | --- | --- |
| 新手 | 2:04 – 3:31 | 8 – 16 | 6.33 |
| 熟练 | 3:20 – 3:55 | 14 – 16 | 4.41 |
| 硬核 | 3:13 – 4:04 | 12 – 16 | 3.05 |

- 单局时长均值 **3:39**，落在 PRD 的 3–8 分钟带内；高手靠技术能把上限推到 8 分钟外。
- Boss 耗时实测：W10 ≈ 53s · W20 ≈ 77s · W30 ≈ 89s。
- **敌机子弹峰值**：第 20 波 ≈ 430 · 第 30 波 ≈ 700 · **第 40 波之后才触顶（900）**。
  真实玩家死在第 15 波附近，所以触顶只发生在「血量恒满」的计量局里 ——
  这是优雅降级（屏幕本就饱和），不是缺陷。断言把「真实局从不触顶」单独立为不变量。
- **敌机池**在第 40 波后持续打满约 10% 的时间。这是**难度终局的兜底机制**：
  池满之后生成请求被丢弃、屏幕持续是一堵会开火的墙，单局因此一定会结束。

### 4.3 探针方法论（比数值更重要）

1. **档位只能有一个自变量。** 曾给硬核档单独加高「别贴边」权重，结果它比新手档多挨 23% 的弹 ——
   因为那实际是在惩罚「待在屏幕底部」，而纵版射击里底部就是最安全的位置。
   多变量同时改的探针量不出它想量的事。
2. **用配对差值，不用整体均值。** 局面随机性（n=5 时档位均值差 0.5、标准差 0.9）远大于档位差异，
   直接比均值是在追噪声。同种子跨档位作差才能把信号提出来。
3. **前瞻不是越远越好。** 实测前瞻 > 0.3s 反而让受击数翻 4 倍 ——
   探针看不见尚未生成的弹幕，长前瞻会外推出「此刻还没子弹的空地」，而那片空地马上被齐射填满。
   这不影响游戏设计，但说明**预测模型的有效期受限于它对威胁生成周期的无知**。
4. **主导变量是反应延迟**（20 步 → 10+ 次受击／1 步 → 0 次），方向分辨率次之。

## 7. 计分与连击

```
multiplier = min(5.0, 1 + (combo−1) × 0.1)
击杀得分 = base × multiplier
连击窗口 = 2.2s（无击杀即断连；玩家受伤立即断连）
存活加分 = 12 分/秒
波次奖励 = 250 × wave
Boss     = 6000 × (1 + bossIndex × 0.5)
```

首杀（combo=1）倍率为 1.0 —— 连击奖励的是「连得住」，不是「开了第一枪」。
`combo` 为连续击杀计数，HUD 显示 `x{combo}`；`maxCombo` 进入结算与排行榜。

### 7.1 时间缩放的预算（实测标定）

**普通击杀不做任何时间缩放。** 慢动作只给重击（坦克/精英，0.2s，**冷却 6s**）与 Boss 死亡（0.8s）。

理由是一条被实测推翻的直觉：

| 版本 | 第 22 波慢动作时间占比 |
| --- | --- |
| 每次击杀都触发 | **35%**（最长连续 0.62s） |
| 只给重击 | 19.5% |
| 只给重击 + 6s 冷却 | **≤4%** |

密集波次每秒杀 2–3 只，0.35× 的慢动作会被不断刷新、连成一片 ——
玩家感知到的「击败后卡顿」**不是掉帧，是节奏被反复打断**。
这条必须有断言看守（`balance.mjs`：「慢动作时间占比 < 8%」「最长连续慢动作 < 1.0s」），
否则它会悄悄回来。

> 阈值 1.0s 而不是 0.7s：唯一合法的长慢动作是**玩家死亡**那一次 0.8s 的高潮定格。
> 把它算进「节奏被打断」是在惩罚一个正确的设计。

## 9. 渲染红线

1. **禁止 `ctx.shadowBlur` 进渲染循环**。辉光一律用「同一形状描 N 遍」：外晕（粗、极淡）→ 中晕 → 核心（细、实色）。普通元素 3 层，**仅玩家与 Boss 允许 4 层** —— 到处发光等于没有焦点。
2. **粒子池固定容量、TypedArray、溢出环形覆盖**，容量永不增长。桌面 1600 / 触屏 700（低端降级）。热路径零对象分配。
3. 大量粒子用 `fillRect`（Canvas 2D 最便宜的原语），只有需要形状的（火花/环/残影）才走路径。
4. 深色底上半透明环会看起来像「一块黑影」，alpha 必须 ≥ 0.7。
5. 背景：三层视差星点 + 透视网格 + 偶发霓虹光带。网格用**预计算的段列表**，不逐帧生成坐标。
6. **HUD 与全部界面文字走 DOM**（浏览器排字远比手写位图字体可靠）；Canvas 里只有世界。HUD 刷新**节流到 10Hz**。

### 9.1 ★ 填充率才是主要成本，不是路径复杂度

这是本项目最贵的一次教训。第 24 波（60 敌机 / 460 弹幕）掉到 **33fps** 时，
我先猜「新敌机的机身从 5 个顶点涨到 12 个、还乘 3 层辉光」——
**猜错了两次**：削减描边宽度、把机身预渲染成精灵，合计只回了 ~4fps。

把每帧覆盖的像素数算一遍，答案立刻清楚：

| 层 | 每帧覆盖像素 |
| --- | --- |
| 全屏底色渐变填充 | 1.30 M |
| **全屏星云 alpha 混合 blit** | 1.30 M |
| **留边压暗（4 个半透明矩形）** | 0.76 M |
| 全部敌机精灵加起来 | 0.30 M |

背景 3.36 M vs 敌机 0.30 M —— 真凶是背景的**填充面积**，而其中大部分是**冗余**的：

1. **把底色渐变与星云烘焙成一张不透明图层** → blit 从「alpha 混合」变成「不透明拷贝」。
2. **背景只画战场 + 外扩 90 单位**，留边填平色。留边本来就只是画框，
   在里面铺满星空 + 星云 + 网格，每帧要多混合 70 万像素，然后被压暗掉。
3. **删掉留边的 4 次半透明压暗** —— 从源头不画星空，比画完再压暗便宜得多。

结果：**33 → 60 fps**，同密度。

> 教训：性能问题先算**像素账**（面积 × 次数），再猜**路径账**（顶点数 × 描边数）。
> 我按路径账猜了两次都错，按像素账一次就中。
> 另外：帧内 JS 耗时只有 1~2ms 时，说明瓶颈在光栅化（离主线程），
> 用 CPU 计时永远量不到 —— 这时只能看**帧间隔**。

### 9.2 自适应 LOD：降级只发生在最乱的时刻

- 敌机细节（眼珠/尾焰/炮塔）在 **> 55 只**时关闭
- 敌方子弹辉光层在 **> 380 发**时关闭（核始终保留）
- 敌机引擎尾迹在 **> 45 只**时停发

阈值定在 55 的依据：平衡实测显示熟练玩家死在**第 14~16 波（约 30~45 只）**，
所以**整局典型体验里细节始终全开**，LOD 只在晚期兜底。
「轮廓 + 血条弧 + 受击闪白」**永不降级** —— 它们是可读性的一部分。

`e2e.mjs` 因此分**两个密度**断言帧率：典型密度（第 14 波）≥ 55 且必须满细节，
晚期密度（第 24 波）≥ 45 允许降级。只测晚期会把标准定得过松，只测典型又漏掉晚期崩塌。

## 10. 存档

键 `neonvoid.save.v1`，schema：

```js
{ v:1, player_name, high_score, total_games, total_kills,
  best_combo, best_time, best_wave,
  settings:{ sound, music, shake },
  leaderboard:[{ name, score, kills, combo, time, wave, date }] }  // 保留最近 50 条，榜页展示前 10
```

三条纪律：
1. **版本字段必需，不符即丢弃重建**（不写迁移代码）。
2. 所有 `localStorage` 访问包 `try/catch` —— 隐私模式下它**抛异常**而非返回 null；失败降级为内存态并在界面明示。
3. 写入**不进热路径**（同步 API，逐帧写会阻塞主线程）。只在开局/结算/改设置时写。

界面必须明示：**清除浏览器缓存会丢失存档；排行榜仅限本机，不同设备不互通。**

## 12. 验证（双层，缺一不可）

### 第 1 层 · `node scripts/verify.mjs`（纯逻辑，不需要浏览器）

- **逐文件 `node --check`** —— `node --check src/main.js` **不跟随 import**，必须逐文件跑
- 文件规模：`src/` 单文件 ≤ 300 行（由断言看守，不是写在文档里就算数）
- 难度曲线单调不减 · 敌机成本表与解锁门槛自洽 · Boss 每 10 波
- 物理确定性：相同输入序列两次运行**逐位相同**
- 扫掠碰撞不穿透（760 u/s 逐子偏移压力测试）
- 判定半径 ≤ 视觉体积（防「看不见的死亡」）
- 计分与连击数学边界（倍率封顶、窗口断连、受伤断连）
- 存档：往返无损 · 版本不符丢弃 · 排行榜裁剪到 50 · 损坏 JSON 不抛异常
- 粒子池：溢出后容量不增长、环形覆盖生效
- 音频：无 Web Audio 环境下全部调用为 no-op

### 第 2 层 · `node scripts/e2e.mjs`（真实 Chrome + CDP）

启动 Chrome 与跑验证**必须在同一个 Node 进程**（工具会回收进程树）。
1. 首屏零控制台异常（**必须有 `<link rel="icon">`**，否则 `/favicon.ico` 404 污染断言）
2. 画布非空白 —— 但**按调色板确切颜色逐层数像素**（"不同颜色数 > N" 是弱断言，少画一整层照样通过）
3. 真实键盘事件（`Input.dispatchKeyEvent`，不是 DOM dispatchEvent）
4. 从 `window.__NV.state()` 读**数值**比对，不看截图猜
5. 完整跑一局直到死亡 → 结算页出现 → 分数与击杀数 > 0
6. 实测帧率 ≥ 55（肉眼分辨不出 52 与 60，必须读数字）
7. 390px 窄屏无横向溢出 · 触屏用 `Input.dispatchTouchEvent` 真实触摸
8. **双方向**：触屏下有摇杆控件 **且** 桌面端连 `body.touch-ui` 类都不存在

本机注意：PATH 需显式 export；本地服务要 `--no-proxy-server`；Chrome 需 `dangerouslyDisableSandbox`；长脚本用后台任务跑。

### 12.2 本机坑（都踩过，别再踩）

1. **`child_process` 在本沙箱被完全阻断** —— 连 `spawnSync('cmd.exe')` 都是 `EBUSY`。
   所以 `node --check`（需要 spawn）这条路走不通。自检改用**进程内动态 `import()`**：
   它既解析又加载，比 `--check` 更强。唯一例外是 `src/main.js`（模块顶层访问 DOM），
   用**失败类型**区分它 —— `SyntaxError` 才算语法错误，DOM 缺失不算。
2. **静态服务器也是「进程树回收」的受害者**。只在上一轮工具调用里 `detached + unref`
   起过服务器，这一轮它已经死了，表现为 Chrome 的 `net::ERR_CONNECTION_REFUSED` ——
   看起来像"服务器没配好"，其实是生命周期问题。
   **修法：`e2e.mjs` 自己起服务器**（已经有人响应就复用），全程单进程。
3. **headless 默认窗口只有 758×426**。在那个尺寸下游戏区被压到 284px 宽，
   宽屏侧栏布局根本不会被触发 —— 桌面试必须显式
   `Emulation.setDeviceMetricsOverride(1440×900)`。
   同理，**测试结束不要用 `clearDeviceMetricsOverride` 恢复**，那会退回 758×426；
   要再显式设一次目标尺寸。
4. **多模态读图不一定可用**。降级方案是自己解码 PNG（`node:zlib`，五种行滤波器全实现）
   再降采样成字符画。两个必须做对的细节：
   - 一格取**最饱和的像素**而不是平均值 —— 1.5px 的霓虹细线摊进 13px 的格子会被平均成背景色；
   - **低亮度用小写字符、高亮度用大写** —— 只判色相会把"很暗的星空底"和"明亮的霓虹"
     画成同一个字符，看起来整屏都是同一种颜色，完全读不出层次与焦点。

### 12.3 断言写错的三类（比代码错更常见）

`新增断言第一次失败时，先问「它想断言的事，在这份代码里本来成立吗？」`

| 类型 | 实例 | 教训 |
| --- | --- | --- |
| **真值判断反了** | `ENEMY_COLOR` 有 6 个键（含 Boss），而 `ENEMY_DEFS` 只有 5 类 → 断言"数量相等"必然失败 | Boss 有独立模块，颜色表本就该多一项 |
| **自相矛盾** | 用 `debugDamagePlayer`（它的设计就是**清掉**无敌帧）去断言"进入无敌帧" | 测试接缝的语义要与断言一致，否则改用真实路径（`hitPlayer`） |
| **写死魔法数** | 断言粒子池"跑 40 步后全部回收"，而池里最长寿命是 5s（还带 ±30% 抖动） | 步数必须从池内**实际**最长寿命推出来，写死迟早偶发失败 |

还有一条更隐蔽的：**`render()` 管线里，生成发生在碰撞求解之后**。
所以"刚在 y<0 出生的敌机与子弹重叠"是正常的一帧延迟，不是漏判。
断言必须把这类"结构性的时间差"显式排除，否则会去修一个没坏的东西。

### 12.4 被断言抓到的真实缺陷

- **`p.radius` 从未定义**（半径只在配置常量上）。`p.radius + eb.rad[i]` = `NaN`，
  所有 `<= r*r` 比较恒为 false —— **玩家对子弹、撞机、掉落全部免疫**，且没有任何报错。
  这类「NaN 让判定静默失效」是最难查的一类，所以有一条专门断言
  「玩家判定半径是有限正数」。
- **`PAL.red` / `PAL.gold` 从未定义**。`strokeStyle = undefined` 会让 Canvas
  **保留上一次的颜色**，于是 Boss 有可能被画成上一只敌机的绿色。
  这条由「PAL 每个 token 都被实际引用」的断言抓到。
- **波次难度会触顶**：`speed/hp/fire` 三个倍率都在第 31 波封顶，此后难度恒定 ——
  高手可以永远活下去。改为由「敌机池被打满」兜底终局。
- **驻留型敌机（坦克/精英）永不离场**：被无视的坦克会永久占位，
  敌机池迟早被这类僵尸填满，晚期波次会**静默地生成不出任何东西**。
  加了 `holdMax`（9s / 11s）让它们攻击一段时间后脱离。
- **每次击杀都触发慢动作** → 游戏 35% 的时间停在 0.35× 速度，
  玩家报「击败后卡顿」。见 §7.1。
- **`const cos = Math.cos` 这类模块级别名在拆分文件时会漏掉**：
  把 `drawBoss` 拆到新文件后别名留在原处，Boss **每帧抛 ReferenceError**——
  而 `requestAnimationFrame` 在 `frame()` 开头就重新排了队，所以它**不崩、只是持续掉帧**。
  这类"不崩溃的错误"只能靠控制台断言抓（e2e 的「全程无控制台异常」）。
- **背景每帧 ~3.4M 像素的冗余填充** → 见 §9.1。
